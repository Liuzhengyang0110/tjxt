# 天机学堂文本与语音互转 · 面试复习

本文档根据 `tj-aigc` 模块当前实际代码整理，覆盖文字转语音（TTS）和语音转文字（STT/ASR）的业务流程、协议选型、Nacos 配置、关键实现、踩坑处理、测试方案及常见面试追问。

> 整理时间：2026-09。模型能力和接口地址可能更新，上线前应再次核对阿里云百炼官方文档。

## 一、30 秒项目介绍

项目在 `tj-aigc` 服务中实现了双向语音能力：文字转语音使用阿里云百炼 DashScope Java SDK，通过 WebSocket 调用 `qwen-audio-3.0-tts-flash`，然后利用 `ResponseBodyEmitter` 将 MP3 音频分片持续写回前端；语音转文字使用 `qwen-audio-3.0-asr-flash` 的同步 HTTP API，接收前端上传的音频文件，识别格式后转成 Base64 Data URI 调用模型，并使用 OpenCC4J 将可能出现的繁体结果统一转成简体。模型密钥、地址、音色和超时等参数统一放在 Nacos 中管理。

## 二、核心名词

### 1. TTS

TTS 是 Text To Speech，即文字转语音。

本项目使用：

```text
qwen-audio-3.0-tts-flash
```

输入是文本，输出是 MP3 音频字节流。

### 2. STT 与 ASR

STT 是 Speech To Text，ASR 是 Automatic Speech Recognition。两者在本项目中都表示语音转文字，只是命名角度不同：

- `/audio/stt`：面向业务的简化接口，只返回识别文本。
- `/audio/asr`：面向调试和扩展的详细接口，返回文本、DashScope 请求 ID 和计费时长。

本项目使用：

```text
qwen-audio-3.0-asr-flash
```

它属于录音结束后再识别的非实时模型，不是边说边返回文字的实时模型。

### 3. 实时与非实时识别

- 实时识别：用户说话过程中持续上传音频帧并接收中间文字，通常使用 WebSocket，例如 `qwen-audio-3.0-asr-flash-streaming`。
- 非实时识别：用户结束录音后上传完整文件，一次性获取结果，本项目采用这种方式。

## 三、为什么三类模型使用不同的调用方式

### 结论

能否使用 OpenAI SDK，取决于供应商是否兼容对应的 OpenAI 接口协议，而不是取决于模型属于 OpenAI、DeepSeek 还是千问。

本项目当前的调用关系如下：

| 功能 | 模型 | 接入方式 | 原因 |
| --- | --- | --- | --- |
| 普通文本对话 | DeepSeek/OpenAI 兼容模型 | Spring AI `openAiChatModel` | 聊天接口兼容 OpenAI Chat Completions 协议 |
| 文字转语音 | `qwen-audio-3.0-tts-flash` | DashScope Java SDK + WebSocket | 该语音模型使用 DashScope 原生实时语音协议 |
| 语音转文字 | `qwen-audio-3.0-asr-flash` | DashScope JSON HTTP API | 该模型不是 OpenAI `/v1/audio/transcriptions` multipart 协议 |

### 面试回答

OpenAI 兼容通常只代表某一个接口族兼容。例如厂商可能兼容 `/v1/chat/completions`，所以聊天可以复用 OpenAI SDK，但它的 TTS、ASR、图片或实时接口未必兼容。`qwen-audio-3.0-asr-flash` 使用 DashScope 的 `multimodal-generation` 地址，请求体是包含 Base64 Data URI 的 JSON；OpenAI STT 一般是 multipart 文件上传，两者 URL、请求体和响应结构均不同，因此不能直接替换 Base URL 后继续使用 OpenAI 音频 SDK。

## 五、Nacos 配置

推荐在 `aigc-service.yaml` 中配置：

```yaml
tj:
  ai:
    dashscope:
      # 建议由环境变量提供，不要把真实 Key 提交到 Git
      key: ${ALIYUN_API_KEY}

      # TTS 原生 WebSocket 地址
      websocket-url: wss://dashscope.aliyuncs.com/api-ws/v1/inference

      tts:
        model: qwen-audio-3.0-tts-flash
        voice: longanhuan_v3.6
        response-format: mp3
        speed: 1.0
        timeout-ms: 120000

      asr:
        url: https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation
        model: qwen-audio-3.0-asr-flash
        # 文件名和 Content-Type 都不能判断格式时才使用该兜底值
        format: wav
        language-hints:
          - zh
        max-file-size: 7MB
        timeout-ms: 120000
```

本地 `application.yml` 还配置了 Spring Multipart 限制：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 7MB
      max-request-size: 8MB
```

### 为什么不建议固定 `sample-rate: 16000`

`sample_rate` 是可选参数。浏览器 `MediaRecorder` 常见输出是 `webm/opus`，实际采样率可能是 48kHz。如果配置写死 16kHz，但文件真实采样率不是 16kHz，参数和音频内容就会不一致。对于 WAV、MP3、WebM 等带有格式信息的文件，可以让服务端自行读取采样率；只有能够保证输入确实是固定采样率时才显式配置。

### 配置绑定

`DashScopeAudioProperties` 使用：

```java
@Configuration
@ConfigurationProperties(prefix = "tj.ai.dashscope")
public class DashScopeAudioProperties {
    private String key;
    private String websocketUrl;
    private Tts tts;
    private Asr asr;
}
```

相比在业务代码中大量使用 `@Value`，类型化配置具有以下优点：

- 层级与 Nacos YAML 一致。
- TTS 和 ASR 配置职责清晰。
- `DataSize`、数字、列表等类型可以自动转换。
- 便于提供默认值和统一校验。
- 新增配置项时更容易维护。

## 六、TTS：文字转语音实现

### 1. Controller

```java
@NoWrapper
@PostMapping(value = "/tts-stream", produces = "audio/mpeg")
public ResponseBodyEmitter ttsStream(@RequestBody String text) {
    return audioService.ttsStream(text);
}
```

最终地址：

```text
POST /audio/tts-stream
```

经过网关访问：

```text
POST /ais/audio/tts-stream
```

### 2. 为什么必须使用 `@NoWrapper`

项目默认会把正常返回值包装成：

```json
{
  "code": 200,
  "msg": "OK",
  "data": "..."
}
```

但 TTS 返回的是 MP3 二进制流。如果进行统一 JSON 包装，音频字节会被破坏，浏览器无法直接播放。因此 TTS 方法通过 `@NoWrapper` 跳过响应包装，并明确声明：

```text
Content-Type: audio/mpeg
```

### 3. 请求文本兼容处理

`extractText()` 兼容三种请求体：

```text
你好
```

```json
"你好"
```

```json
{"text":"你好"}
```

这样可以避免前端以 JSON 字符串传输时，模型实际收到多余的双引号。

### 4. 构造模型参数

```java
SpeechSynthesisParam param = SpeechSynthesisParam.builder()
        .apiKey(properties.getKey())
        .model(tts.getModel())
        .voice(tts.getVoice())
        .format(resolveAudioFormat(tts.getResponseFormat()))
        .speechRate(tts.getSpeed())
        .build();
```

当前代码固定输出：

```text
MP3 / 24000Hz / 单声道 / 256kbps
```

虽然配置保留了 `response-format`，但当前 HTTP 接口的响应类型固定为 `audio/mpeg`，所以非 MP3 配置只会记录警告，不会改变实际输出格式。

### 5. 流式发送过程

核心调用：

```java
SpeechSynthesizer synthesizer = new SpeechSynthesizer(param, null);

Disposable disposable = synthesizer.callAsFlowable(text).subscribe(
        result -> sendAudioFrame(emitter, result),
        error -> emitter.completeWithError(error),
        emitter::complete
);
```

处理过程可以概括为：

1. Controller 创建请求。
2. Service 校验文本和 API Key。
3. DashScope SDK 通过 WebSocket 发起语音合成。
4. SDK 每收到一个 `ByteBuffer` 音频分片，就立即发送给 `ResponseBodyEmitter`。
5. 前端可以边接收边缓存或播放，不必等完整 MP3 全部生成。
6. 完成、错误或超时时释放订阅并关闭 WebSocket。

### 6. 为什么使用 `ResponseBodyEmitter`

`ResponseBodyEmitter` 是 Spring MVC 的异步响应工具，适合一个 HTTP 请求中多次写出数据。本项目主 Web 技术栈是 Spring MVC，而 DashScope TTS SDK 返回 RxJava `Flowable`，两者可以通过订阅回调自然衔接。

与一次性返回 `byte[]` 相比：

- 首包延迟更低。
- 不需要在后端内存中缓存完整音频。
- 长文本合成体验更好。
- 可以在生成过程中及时处理异常和取消。

### 7. 资源清理

代码同时监听：

```java
emitter.onTimeout(cleanup);
emitter.onError(error -> cleanup.run());
emitter.onCompletion(cleanup);
```

`AtomicBoolean` 保证 WebSocket 只关闭一次，`AtomicReference<Disposable>` 保存 RxJava 订阅，确保客户端中断、服务异常或超时时不会遗留连接和订阅。

这是面试中可以强调的可靠性设计：功能跑通之外，还考虑了异常路径下的资源释放。

## 七、STT/ASR：语音转文字实现

### 1. Controller

详细结果接口：

```java
@PostMapping(value = "/asr", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public AsrVO asr(@RequestPart("audioFile") MultipartFile file) {
    return audioService.asr(file);
}
```

简化文本接口：

```java
@PostMapping(value = "/stt", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public String stt(@RequestPart("audioFile") MultipartFile file) {
    return audioService.stt(file);
}
```

注意 Multipart 字段名必须是：

```text
audioFile
```

如果前端传的是 `file`，Spring 会提示缺少请求 Part。

### 2. 两个接口的区别

`/audio/stt` 返回：

```text
欢迎来到天机学堂。
```

`/audio/asr` 返回：

```json
{
  "text": "欢迎来到天机学堂。",
  "requestId": "req-xxx",
  "durationSeconds": 4
}
```

通过网关调用时，项目还会在外层包装统一的 `R` 对象。

### 3. 输入校验

调用模型前依次校验：

- 文件对象不能为 `null`。
- 文件内容不能为空。
- DashScope API Key 必须存在。
- ASR URL 和模型名必须存在。
- 文件大小不能超过配置的 `max-file-size`。
- 文件格式必须在允许列表中。

当前支持：

```text
aac、amr、avi、flac、flv、m4a、mkv、mov、mp3、mp4、mpeg、
ogg、opus、wav、webm、wma、wmv
```

### 4. 音频格式识别

格式判断优先级：

1. 原始文件名后缀。
2. Multipart `Content-Type`。
3. Nacos 中的 `asr.format` 兜底配置。

例如浏览器上传：

```text
filename = recording.webm
Content-Type = audio/webm
```

后端会把 DashScope 参数中的 `format` 设置成 `webm`，而不是错误地固定成 `wav`。

### 5. 为什么后端要转成 Base64 Data URI

浏览器向本项目上传文件使用 multipart，但 `qwen-audio-3.0-asr-flash` 的 DashScope 接口要求 JSON，请求中的音频可以是公网 URL 或 Base64 Data URI。本项目没有先把临时录音上传到 OSS，因此采用 Base64：

```text
data:audio/webm;base64,GkXfo59ChoEBQveBAULyg...
```

Base64 编码后的体积大约是原文件的 4/3，再加上 Data URI 前缀。官方接口对 Base64 输入有限制，因此本项目把原文件限制为 7MB，为编码膨胀和 JSON 开销预留空间。

### 6. DashScope 请求结构

项目发送的核心 JSON：

```json
{
  "model": "qwen-audio-3.0-asr-flash",
  "input": {
    "messages": [
      {
        "role": "user",
        "content": [
          {
            "type": "input_audio",
            "input_audio": {
              "data": "data:audio/webm;base64,..."
            }
          }
        ]
      }
    ]
  },
  "parameters": {
    "format": "webm",
    "language_hints": ["zh"]
  }
}
```

请求头：

```text
Authorization: Bearer <DashScope API Key>
Content-Type: application/json
X-DashScope-SSE: disable
```

`X-DashScope-SSE: disable` 表示本项目上传完整音频后，只接收最终识别结果。

### 7. HTTP 客户端

当前实现使用 JDK `HttpClient`：

```java
HttpClient.newBuilder()
        .followRedirects(HttpClient.Redirect.NORMAL)
        .connectTimeout(Duration.ofSeconds(10))
        .build();
```

每次 ASR 请求还会使用 Nacos 的 `timeout-ms` 设置整体超时。这样连接超时和业务请求超时是两个不同层次：

- 连接超时：无法与远端服务器建立连接时尽快失败。
- 请求超时：连接成功但模型长时间没有完成识别时终止等待。

### 8. 响应解析

不同版本或调用形式的 DashScope 响应字段可能略有区别，代码按以下顺序兼容读取：

```text
output.text
output.sentence.text
output.output.sentence.text
```

如果三个位置都没有文本，则抛出业务异常，不向前端返回伪成功。

详细结果 `AsrVO` 包含：

```java
private String text;
private String requestId;
private Long durationSeconds;
```

其中 `requestId` 用于结合阿里云日志排查问题，`durationSeconds` 可用于计费统计和监控。

### 9. 繁体转简体

ASR 结果可能出现繁体中文，因此项目引入 OpenCC4J：

```xml
<dependency>
    <groupId>com.github.houbb</groupId>
    <artifactId>opencc4j</artifactId>
    <version>1.14.0</version>
</dependency>
```

解析出文本后执行：

```java
text = ZhConverterUtil.toSimple(text);
```

例如：

```text
歡迎來到天機學堂。
```

转换为：

```text
欢迎来到天机学堂。
```

将转换放在 Service 实现层，而不是 Controller，可以确保 `/stt` 和 `/asr` 两个入口得到一致的简体结果。

## 八、统一响应包装器问题

### 1. 问题背景

项目自定义了 `WrapperResponseMessageConverter` 和统一响应包装逻辑。普通网关请求会被包装成 `R<T>`，但 Spring AI 底层 HTTP 客户端也可能复用 Spring 注册的消息转换器。

如果自定义转换器错误介入模型请求，文件、multipart 或模型协议对象可能被当成普通业务响应处理，最终出现消息转换异常。

### 2. 已有的跳过判断

`WrapperResponseMessageConverter.canWrite()` 中会检查：

```java
Object springAIIdentification =
        WebUtils.getAttribute(Constant.SPRING_AI_ATTR);

if (ObjectUtil.equal(springAIIdentification, Constant.SPRING_AI_FLAG)) {
    return false;
}
```

返回 `false` 表示当前自定义包装转换器不参与本次 Spring AI 数据转换。

### 3. RetryTemplate 监听器

`SpringAIConfig` 给 Spring AI 共用的 `RetryTemplate` 注册监听器：

```java
@Bean
public RetryListener customizeRetryTemplate(RetryTemplate retryTemplate) {
    RetryListener retryListener = new RetryListener() {
        @Override
        public <T, E extends Throwable> boolean open(
                RetryContext context, RetryCallback<T, E> callback) {
            WebUtils.setAttribute(
                    Constant.SPRING_AI_ATTR,
                    Constant.SPRING_AI_FLAG
            );
            return true;
        }

        @Override
        public <T, E extends Throwable> void close(
                RetryContext context,
                RetryCallback<T, E> callback,
                Throwable throwable) {
            WebUtils.removeAttribute(Constant.SPRING_AI_ATTR);
        }
    };
    retryTemplate.registerListener(retryListener);
    return retryListener;
}
```

执行时机：

- `open()`：Spring AI 重试流程开始前设置请求属性。
- `close()`：成功或最终失败后删除属性。
- 转换器看到属性后跳过自定义包装。
- 使用 `close()` 统一清理，避免属性污染同一请求中的后续业务。

### 4. 与当前千问 ASR 的关系

当前 `qwen-audio-3.0-asr-flash` 实现使用 JDK `HttpClient`，不会经过 Spring MVC 的 `HttpMessageConverter`，所以 ASR 本身不依赖这个监听器。

补充监听器仍然有价值，因为项目的聊天模型等 Spring AI 调用会使用共用的 `RetryTemplate`。如果未来切换到 Spring AI 原生音频模型，也已经具备跳过包装器的保护。

面试时要避免说成“所有千问 ASR 都必须添加监听器”。准确表述应是：这是项目自定义消息转换器与 Spring AI 客户端共存时的隔离措施，而不是 DashScope 模型本身的要求。

## 九、异常处理与安全设计

### 1. API Key

- Key 只通过配置注入，不写入 Java 代码。
- 推荐 Nacos 引用环境变量，例如 `${ALIYUN_API_KEY}`。
- 不在日志中打印 Key、Authorization 请求头或完整 Base64 音频。
- 如果 Key 曾出现在聊天记录、Git 或日志中，应立即轮换。

### 2. 文件安全

- 上传大小在 Spring Multipart 层和业务层双重限制。
- 只允许白名单音频/视频封装格式。
- 不信任前端声明的固定格式，会结合后缀和 Content-Type 判断。
- 当前实现直接在内存中读取文件，因此限制 7MB，避免单请求占用过多内存。

### 3. 超时

- TTS 使用 `ResponseBodyEmitter` 超时回调释放订阅和 WebSocket。
- ASR 设置连接超时和请求超时。
- `InterruptedException` 被捕获后重新调用 `Thread.currentThread().interrupt()`，保留线程中断状态。

### 4. 上游错误

DashScope 返回非 2xx 时：

- 尝试从 JSON 的 `message` 或 `output.message` 中提取错误。
- 非 JSON 错误按纯文本处理。
- 最多保留 500 个字符，避免超长 HTML 错误污染日志和接口。
- 对外抛出统一业务异常。

### 5. 重试

音频请求不适合对所有错误无条件重试：

- 400、401、403 等参数或鉴权错误重试没有意义。
- 429 应尊重服务端限流并进行退避，不能立即连续重试。
- 连接超时、少量 5xx 可以设置有限次数的指数退避。
- TTS 流已经向前端写出部分字节后不能简单从头重试，否则可能拼接出损坏音频。

## 十一、常见故障排查

### 1. `Required part 'audioFile' is not present`

原因：前端 Multipart 字段名写成了 `file` 或其他名称。

解决：

```javascript
formData.append('audioFile', blob, 'recording.webm');
```

### 2. 提示不支持的音频格式

检查：

- 文件名是否带正确后缀。
- 前端是否设置了正确的 Blob MIME 类型。
- 文件内容是否与扩展名一致。
- Nacos `asr.format` 兜底值是否合理。

### 3. 上传文件超过限制

可能有两层错误：

- Spring 在进入 Controller 前因 Multipart 大小限制拒绝。
- Service 根据 `max-file-size` 主动拒绝。

若要提高限制，还必须考虑 Base64 膨胀、JVM 内存和 DashScope 接口限制，不能只修改一个数字。

### 4. TTS 返回 JSON，不能播放

检查：

- Controller 是否保留 `@NoWrapper`。
- `produces` 是否为 `audio/mpeg`。
- 网关或统一响应插件是否再次包装了二进制结果。
- 前端是否把响应类型设置为 `blob` 或 `arraybuffer`。

### 5. ASR 模型调用失败

检查：

- `tj.ai.dashscope.key` 是否有值。
- Key 所属地域与接口地址是否一致。
- Nacos 模型名是否为 `qwen-audio-3.0-asr-flash`，不能误写成 streaming 模型。
- 上传音频是否超过时长或大小限制。
- `format` 是否与真实文件一致。
- 日志中的 DashScope `requestId` 和上游错误信息。

### 6. ASR 结果仍有繁体

检查：

- `opencc4j` 是否成功进入运行时依赖。
- 是否统一经过 `parseAsrResponse()`。
- 是否存在其他接口绕过 Service，直接返回上游原始文本。

### 7. 消息转换异常

检查：

- `WrapperResponseMessageConverter` 是否判断 `SPRING_AI_ATTR`。
- `customizeRetryTemplate()` 是否被 Spring 扫描并注册。
- `open()` 是否设置标识，`close()` 是否删除。
- 若模型调用发生在线程切换后的异步任务中，请求属性可能不会自动传播，此时应为 AI 客户端配置独立的消息转换器，而不是继续依赖 Servlet 请求属性。

## 十二、面试高频问题

### Q1：为什么聊天能用 OpenAI SDK，千问语音却不能直接用？

**简要回答：**

因为 SDK 复用取决于接口协议兼容性。聊天模型兼容 OpenAI Chat Completions，所以替换 Base URL、Key 和模型名即可；千问 TTS 使用原生 WebSocket，`qwen-audio-3.0-asr-flash` 使用 DashScope JSON HTTP API，与 OpenAI 音频接口的 URL、请求体和响应结构不同，因此分别使用 DashScope SDK和自定义 HTTP 调用。

### Q2：为什么 TTS 使用流式响应？

**简要回答：**

语音生成需要时间，流式返回可以在首批音频生成后立即发送给前端，降低首包延迟，并避免服务端缓存完整音频。项目使用 DashScope RxJava `Flowable` 接收分片，再用 Spring MVC `ResponseBodyEmitter` 写回客户端。

### Q3：为什么 TTS 不能走统一响应包装？

**简要回答：**

统一包装面向 JSON 业务对象，而 TTS 返回 MP3 二进制数据。包装后会改变字节内容和 Content-Type，音频文件无法播放，所以使用 `@NoWrapper` 并返回 `audio/mpeg`。

### Q4：为什么 ASR 没有直接把 MultipartFile 发给 DashScope？

**简要回答：**

浏览器到业务服务使用 multipart，但当前模型的 DashScope 接口要求 JSON，音频字段支持 URL 或 Base64 Data URI。项目没有把临时录音先上传到 OSS，因此读取文件后进行 Base64 编码并嵌入 JSON。

### Q5：Base64 有什么缺点？

**简要回答：**

Base64 会增加约三分之一的体积，同时在 JVM 中产生原始字节、Base64 字符串和完整 JSON 等多份内存。它适合短录音和中小文件，不适合大文件或高并发。生产环境处理长录音时，更适合先上传 OSS，再向模型传递临时 URL。

### Q6：为什么要同时保留 `/stt` 和 `/asr`？

**简要回答：**

`/stt` 只返回文本，方便聊天输入框直接使用；`/asr` 返回 requestId 和音频时长，便于排错、监控和计费。两个接口复用同一个识别实现，不会形成两套逻辑。

### Q7：为什么需要 OpenCC4J？

**简要回答：**

模型输出可能混有繁体字，而业务页面希望统一使用简体中文。项目在 Service 层解析完文本后调用 `ZhConverterUtil.toSimple()`，保证所有对外入口得到一致结果。转换属于展示规范化，不改变原始音频。

### Q8：音频格式是怎样识别的？

**简要回答：**

优先使用文件扩展名，其次根据 Content-Type 映射，最后使用 Nacos 的默认格式。这样既支持正常文件上传，也兼容浏览器生成的 `webm/opus` Blob，并避免把所有文件错误声明成 WAV。

### Q9：为什么文件大小要双重限制？

**简要回答：**

Spring Multipart 限制可以在解析请求时尽早拒绝过大文件，业务层限制可以保护直接调用 Service 或配置不一致的场景。双重限制属于纵深防御，并且能够降低 Base64 编码造成的内存压力。

### Q10：RetryTemplate 监听器解决了什么问题？

**简要回答：**

项目自定义的消息转换器用于包装网关业务响应，但 Spring AI 客户端也可能使用 Spring 消息转换基础设施。监听器在 Spring AI 重试流程开始时设置请求标识，使自定义转换器主动退出；调用结束后清理标识，避免影响正常业务响应。

### Q11：`ResponseBodyEmitter`、SSE 和 WebSocket 有什么区别？

**简要回答：**

`ResponseBodyEmitter` 是服务端在一个 HTTP 响应中多次写数据的 Spring MVC 编程模型；SSE 是基于 HTTP 的文本事件协议；WebSocket 是全双工长连接协议。本项目 TTS 的上游是 DashScope WebSocket，下游是普通 HTTP 音频流，并没有把 WebSocket 原样暴露给前端。

### Q12：实时 STT 应如何改造？

**简要回答：**

将模型换成 `qwen-audio-3.0-asr-flash-streaming`，前端边录音边发送音频帧，后端维护与 DashScope 的 WebSocket 会话，并把临时和最终识别结果持续推送给前端。还要处理分片顺序、采样格式、VAD 断句、会话关闭、断线重连和背压，复杂度明显高于当前的文件上传方案。

### Q13：当前实现还有哪些可以优化？

**简要回答：**

- 大文件改成 OSS 临时 URL，减少 Base64 内存开销。
- 使用专用线程池或异步任务，避免长时间占用 Servlet 工作线程。
- 对 5xx 和网络错误做有限次数的指数退避，对 4xx 不重试。
- 添加 Micrometer 指标，统计调用次数、成功率、耗时、音频时长和错误码。
- 对用户级并发和文件大小做限流。
- 使用业务空间专属域名，并保证地域、Workspace 和 Key 匹配。
- 如果配置需要动态刷新，避免在请求中反复修改 SDK 全局静态地址。
- 保存原始识别结果或审计摘要时，评估隐私、保留期限和脱敏要求。

## 十三、生产环境改进方向

### 1. 短录音与长录音分流

当前方案适合聊天语音输入等短录音。对于会议、课程视频或长音频，应改用文件转写模型，通过 OSS URL 提交异步任务，并使用轮询或事件回调获取结果。

### 2. 避免全量内存加载

当前 `MultipartFile.getBytes()` 会将文件整体读入内存，随后 Base64 和 JSON 又产生额外对象。高并发场景可采用：

- 严格控制短音频大小。
- 上传对象存储后传 URL。
- 限制同一用户并发。
- 监控堆内存和 GC。

### 3. 可观测性

建议记录但不泄露敏感数据：

- 业务 requestId。
- DashScope requestId。
- 模型名和音频格式。
- 原始文件大小与识别时长。
- TTS 首包延迟和总耗时。
- 上游状态码和错误码。
- 成功率、超时率与限流次数。

不要记录：

- API Key。
- Authorization 请求头。
- 完整 Base64 音频。
- 未经授权的用户语音内容。

### 4. 配置刷新

Nacos 修改后不应默认假设所有普通 Bean 和第三方 SDK 对象都会自动刷新。模型、Key、地址等关键配置变化后应验证 Bean 是否重建；不能确认时，重启 `aigc-service` 是最稳妥的生效方式。

### 5. SDK 全局变量

TTS 当前通过：

```java
Constants.baseWebsocketApiUrl = properties.getWebsocketUrl();
```

设置 DashScope SDK 全局地址。静态全局配置适合单一地域，但如果未来同一 JVM 中按租户或地域使用多个地址，多个请求之间可能相互覆盖。更好的方式是使用支持实例级 URL 的 SDK 构造参数，或为不同地域创建隔离的客户端实例。

## 十四、面试口述模板

### 1 分钟版本

项目的语音能力分为 TTS 和 STT。TTS 使用千问 `qwen-audio-3.0-tts-flash`，通过 DashScope Java SDK 建立 WebSocket，上游每返回一个音频 ByteBuffer，就用 Spring MVC 的 `ResponseBodyEmitter` 向前端写一个 MP3 分片，同时在完成、异常和超时时释放 RxJava 订阅和连接。因为返回的是二进制音频，所以接口使用 `@NoWrapper` 跳过统一 JSON 包装。

STT 使用 `qwen-audio-3.0-asr-flash` 的同步 HTTP API。前端以 multipart 上传 `audioFile`，后端校验大小和格式，把音频编码成 Base64 Data URI，构造 DashScope 多模态 JSON 请求，然后解析 `output.text`。为了统一中文展示，结果再经过 OpenCC4J 繁转简。配置全部放在 Nacos，并设置文件大小、连接和请求超时。项目还通过 RetryTemplate 监听器隔离 Spring AI 请求与自定义响应包装器，并用本地 Mock HTTP Server 测试请求协议和响应解析。
