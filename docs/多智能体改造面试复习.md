# 天机学堂 AI 对话项目 · 多智能体改造面试复习

> 本文档记录将现有**单智能体**改造为「**路由智能体 + 专项智能体**」过程中沉淀的知识点。
> 结构参考《AI对话项目面试复习.md》，仍采用"难度 — 结论 — 原理 — 项目落地 — 追问"的方式组织。
> 改造目标代码位于 `tj-aigc/.../agent/` 包（设计草稿：`Agent` 接口、`AbstractAgent` 抽象类及各专项 Agent 子类）。
> 已实现功能（Redis 记忆、停止生成、Nacos 提示词等）见《AI对话项目面试复习.md》，本文不再重复展开。

## 〇、改造背景（30 秒口述）

原实现只有一个 `ChatServiceImpl`，把"系统提示词、RAG 检索 Advisor、工具集、toolContext"全部硬编码在同一个聊天流程里。任何用户问题都走同一套配置。

改造目标：把能力拆成**多种类型的智能体**，例如课程推荐、课程咨询、课程购买、知识讲解，再配一个**路由智能体**负责判断用户意图、把请求分发给对应的专项智能体。不同类型用 `AgentTypeEnum` 区分，公共流程收敛到抽象基类，差异点由各子类自己声明，从而做到"一个智能体一套配置、按需启用工具与检索"。

## 一、Java 枚举与类型标识

### Q1：`AgentTypeEnum` 这段枚举是做什么的？为什么用枚举区分智能体？

**难度：基础**

**简要回答：**

`AgentTypeEnum` 给每一类智能体定义"机器代号（`agentName`）+ 中文描述（`desc`）"，作为系统内识别智能体身份的统一类型字典：

```java
ROUTE("ROUTE", "路由智能体"),
RECOMMEND("RECOMMEND", "课程推荐智能体"),
CONSULT("CONSULT", "课程咨询智能体"),
BUY("BUY", "课程购买智能体"),
KNOWLEDGE("KNOWLEDGE", "知识讲解智能体");
```

用枚举而不是字符串常量（`public static final String`）的好处：**类型安全**——只能取枚举里定义的几个值，写错编译期就报错；枚举常量是单例，可直接用 `==` 比较；还能自带 `desc`、`agentNameOf()` 反查等能力。

**项目落地：**

- `agentNameOf(String)`：用 hutool 的 `EnumUtil.getBy(AgentTypeEnum::getAgentName, agentName)` 做"字符串代号 → 枚举"反查，典型场景是路由模型输出一个 `"RECOMMEND"` 之类的字符串，据此找到对应枚举、再路由到专项智能体。
- `getAgentType()` 会被每个 Agent 子类 override，供路由层"找对 Bean"。

**可能追问：**

- 枚举相比字符串常量或 `Map` 有什么优势？
- `EnumUtil.getBy` 找不到时返回什么？（返回 `null`，不抛异常，调用方要判空）
- 如果路由模型输出 `"recommend"`（小写），`agentNameOf` 会怎样？（精确匹配，返回 `null`，需自行 `toUpperCase()` 容错）

### Q2：`toString()` 里的 `name()` 是哪里来的？覆写它有意义吗？

**难度：基础**

**简要回答：**

`name()` 来自**隐式父类 `java.lang.Enum<E>`**。Java 规定任何 `enum` 编译后都自动 `extends Enum<E>`，所以不写 `extends` 也能直接调用继承来的方法：

```java
public final String name() { return name; }   // 返回常量名，如 "ROUTE"
```

而 `Enum` 默认的 `toString()` 本来就是返回 `name`，因此这段覆写：

```java
@Override
public String toString() {
    return this.name();
}
```

**等价于默认行为**，属于"显式声明"：强调无论 `desc` 怎么改成中文，打印/序列化枚举时始终输出英文代号 `ROUTE`，让日志与传给模型的内容语义稳定。

**注意区分两个字段：**

| 表达式 | 来源 | 值 |
|---|---|---|
| `AgentTypeEnum.RECOMMEND.name()` | 编译器从常量标识符生成，不能改 | `"RECOMMEND"` |
| `AgentTypeEnum.RECOMMEND.getAgentName()` | 构造时手动传入的字段 | `"RECOMMEND"`（当前恰好相等） |

`agentName` 字段的真正价值在于：将来重命名枚举常量时，对外代号（模型输出 / DB 存储）可保持不变。

**可能追问：**

- `ordinal()`、`values()`、`valueOf()` 是哪里来的？（`Enum` + 编译器为每个枚举生成的静态方法）
- 枚举可以继承别的类吗？（不能，只能 `implements` 接口）

### Q3：Java 枚举的完整语法有哪些要点？

**难度：基础**

**简要回答：**

枚举本质是一个特殊的类，语法要点如下：

```java
public enum AgentTypeEnum {
    // ① 常量列表必须写在最前面，相当于"调用私有构造器"，末尾若无其他内容可省略分号
    ROUTE("ROUTE", "路由智能体"),
    KNOWLEDGE("KNOWLEDGE", "知识讲解智能体");

    // ② 字段
    private final String agentName;
    private final String desc;

    // ③ 构造器默认就是 private，外部不能 new
    AgentTypeEnum(String agentName, String desc) {
        this.agentName = agentName;
        this.desc = desc;
    }

    // ④ 方法：可覆写、可自定义实例方法、可自定义静态方法
    @Override
    public String toString() { return this.name(); }
    public static AgentTypeEnum agentNameOf(String agentName) { /* ... */ }
}
```

三个硬性约束：

1. **不能 `new`**：枚举常量是单例，只能用 `枚举名.常量名` 引用。
2. **不能 `extends` 其他类**，但可以 `implements` 接口（项目里 `ChatEventTypeEnum implements BaseEnum` 就是示例）。
3. 自带 `name()` / `ordinal()`，以及编译器生成的静态 `values()` / `valueOf()`。

**项目落地：** `AgentTypeEnum` 是"常量 + 字段 + 私有构造器 + `@Getter` + 静态反查方法"的典型写法；`ChatEventTypeEnum` 额外演示了"枚举实现接口"。

**可能追问：**

- 枚举常量在类加载时如何初始化？保证线程安全吗？（类是天然的，枚举单例常用于实现安全单例）
- 想给不同枚举常量不同的行为（如不同智能体返回不同系统提示词），有哪些做法？（接口 + 多态，或枚举内的抽象方法）

## 二、Agent 接口与抽象类设计

### Q4：为什么要定义 `Agent` 接口？`process`（普通对话）和 `processStream`（流式对话）有什么区别？

**难度：中等**

**简要回答：**

把所有智能体共有的操作抽象成 `Agent` 接口，调用方（如路由智能体）只面向接口编程，不依赖具体实现类。接口大致包含：

```java
public interface Agent {
    String process(String question, String sessionId);            // 普通（同步）对话
    Flux<ChatEventVO> processStream(String question, String sessionId); // 流式对话
    AgentTypeEnum getAgentType();                                  // 智能体类型
    void stop(String sessionId);                                   // 停止
    // 以下是"设定/配置"类方法（由子类声明差异）
    String systemMessage();
    Map<String,Object> systemMessageParams();
    List<Advisor> advisors();
    Map<String,Object> advisorParams(String sessionId, String requestId);
    Object[] tools();                                              // 工具集
    Map<String,Object> toolContext(String sessionId, String requestId);
}
```

**`process` 与 `processStream` 的本质区别是"同步整包" vs "异步逐块"：**

| 维度 | `process`（普通/同步） | `processStream`（流式） |
|---|---|---|
| 底层 API | `.call()` | `.stream()` |
| 返回 | 单个完整结果（`String`） | `Flux<ChatResponse>`，边生成边推送 |
| 出结果时机 | 全部生成完才返回 | 逐字/逐块持续输出（打字机效果） |
| 前端体验 | 等待后整段出现 | 首字延迟短，实时显示 |
| 中断 | 难以打断 | 可中断，还能保留已生成部分 |

两者只差 `.call()` / `.stream()`，其余 `system/advisors/tools/toolContext/user` 的装配完全一致。不是所有场景都需要流式：面向用户的客服聊天用 `processStream`，服务端内部处理/脚本可用 `process`。把它们都放进接口，是为了让调用方无需感知子类内部走同步还是流式。

**项目落地：** 改造前的 `ChatServiceImpl` 已用 `.stream()`（Controller 配 `TEXT_EVENT_STREAM_VALUE` 走 SSE），这条路径就是 `processStream` 的实现来源。

**可能追问：**

- `Flux` 与 `Mono` 的区别？
- 什么操作会破坏端到端流式？（`block()`、先 `collectList()`）
- SSE 与 WebSocket 的取舍？

### Q5：为什么需要 `AbstractAgent` 抽象类？把公共实现写在这里有什么好处？

**难度：中等**

**简要回答：**

因为每个智能体 90% 的逻辑相同——`process`/`processStream` 的流程、请求装配的骨架、中断兜底保存历史等。真正不同的只有"系统提示词、工具、Advisor、参数"。抽象类就是**模板方法模式**：父类把公共逻辑写好并确定流程顺序，差异点用抽象方法占位，子类只需填差异。

**公共逻辑（父类写死，子类不用动）：**

| 方法 | 内容 |
|---|---|
| `process` | 生成 requestId → 更新会话时间 → 拼请求 → `.call().content()` |
| `processStream` | 那串 Flux 处理（生成状态控制 / 中断兜底 / PARAM 收尾 / STOP 事件） |
| `getChatClientRequest` | `system → advisors → tools → toolContext → user` 的装配骨架 |
| `advisorParams` | 默认给 `CONVERSATION_ID` |
| `stop` / `generateRequestId` / `saveStopHistoryRecord` | 通用实现 |

**差异点（子类各自 override）：**

| 方法 | 每个智能体的差异 |
|---|---|
| `systemMessage` / `systemMessageParams` | 知识讲解与购买智能体的角色设定完全不同 |
| `advisors` | 知识讲解挂 RAG，购买智能体不挂 |
| `tools` | 购买智能体挂下单工具，咨询/知识讲解不需要 |
| `toolContext` | 需要注入的上下文不同 |
| `getAgentType` | 类型不同 |

**为什么不用"接口 default 方法"或"把实现塞接口里"：**

- 需要持有**成员字段**（`chatClient`、`chatSessionService`、`chatMemory`、静态 `GENERATE_STATUS`、`STOP_EVENT`），接口放不了这些装配细节。
- 抽象类可以隐藏装配逻辑、只暴露少而稳定的方法给子类。

**为什么不直接实例化 `AbstractAgent`：** 差异方法还没填，一个不完整的智能体不该被 `new`，所以声明为 `abstract` 强制用具体子类。

**可能追问：**

- 什么是模板方法模式？和策略模式的区别？
- 父类用 `@Resource` 注入，子类要注意什么？（`AbstractAgent` 本身不能被注册为 Bean；具体子类要能被 Spring 管理，否则注入字段为 null）
- 不用抽象类、用"组合 + 策略"或"接口默认方法"是否可行？各有什么取舍？

## 三、ChatClient 请求装配

### Q6：`chatClient.prompt()` 后面的 `.system()`、`.user()`、`.advisors()`、`.toolContext()` 分别是做什么的？

**难度：中等**

**简要回答：**

`chatClient.prompt()` 返回请求构建器，后续链式调用都在"拼装一次要发给大模型的请求"，最后 `.call()` / `.stream()` 触发发送。

| 构建器方法 | 作用 | 改造前代码里的内容 |
|---|---|---|
| `.system()` | 角色/规则设定（模板 + 占位符） | 从 Nacos 动态加载 + `param("now", 当前时间)` |
| `.user()` | 用户本次提问 | `question` |
| `.advisors()` | 追加本次请求的增强组件（拦截器/中间件） | 动态创建的 `qaAdvisor`（RAG 检索） |
| `.advisors(...).param()` | 给 Advisor 传上下文参数 | `CONVERSATION_ID`（绑定会话记忆） |
| `.toolContext()` | 给 Tools 传"私有上下文" | `REQUEST_ID`、`USER_ID` |

**对照代码（改造前 `ChatServiceImpl`）：**

```java
chatClient.prompt()
        .system(ps -> ps.text(systemPromptConfig.getChatSystemMessage().get())
                       .param("now", DateUtil.now()))
        .advisors(a -> a.advisors(qaAdvisor)
                        .param(ChatMemory.CONVERSATION_ID, conversationId))
        .toolContext(Map.of(Constant.REQUEST_ID, requestId, Constant.USER_ID, userId))
        .user(question)
        .stream().chatResponse();
```

改造后 `AbstractAgent.getChatClientRequest(...)` 把这些**写死的内容替换成对 `this.systemMessage()` / `this.advisors()` / `this.tools()` 等方法的调用**，从而把"每个智能体装什么"下沉给子类决定。

**两个需要区分的"Advisor"：**

- **全局默认 Advisor**（`SpringAIConfig` 里 `defaultAdvisors` 配置的 `SimpleLoggerAdvisor`、`MessageChatMemoryAdvisor`）：所有请求都生效。
- **本次请求 Advisor**（`advisors()` 方法返回）：追加在默认之上，只对该 Agent 的请求生效。

**可能追问：**

- Advisor 的执行顺序？（像过滤器链一样按序执行）
- `system` 里的占位符如何替换？（模板中的 `{{key}}` 与 `.param(key, value)` 对应）

## 四、工具（Tool）机制

### Q7：`.toolContext(...)` 是"给工具查看的信息"吗？准确说法是什么？

**难度：中等**

**简要回答：**

方向正确，但要校准为：**`toolContext` 里的数据不是发给大模型看的，而是放在一旁，等大模型决定调用某个工具时，注入给"工具的执行方法"使用的旁路上下文。**

需要区分"工具的两层"：

| | 工具定义（schema/说明书） | 工具执行方法（真实 Java 方法） |
|---|---|---|
| 谁看到 | 大模型能看到（据此决定调哪个、填什么参） | 大模型看不到实现 |
| `toolContext` 给谁 | ✘ 不掺进 schema | ✔ 注入给执行方法（方法形参接 `ToolContext`） |

大模型只会看到"课程查询、课程预下单"这类**名字与参数说明**，看不到 `userId=123`、`requestId=xxx` 这些具体值——它是盲调，由框架把 `toolContext` 注入工具方法后自行取用。

**项目落地（`OrderTools.prePlaceOrder`）：**

```java
@Tool(description = "...")
public PrePlaceOrder prePlaceOrder(List<Number> ids, ToolContext toolContext) {
    UserContext.setUser(Convert.toLong(toolContext.getContext().get(Constant.USER_ID))); // 身份
    // ... tradeClient.prePlaceOrder(...) 下单
    var requestId = Convert.toStr(toolContext.getContext().get(Constant.REQUEST_ID));
    ToolResultHolder.put(requestId, field, result);   // 结果按 requestId 登记，供前端 PARAM 回传
}
```

`toolContext` 常用于传**不该由模型决定 / 不该出现在对话里**的运行期信息（当前用户 id、token、traceId、请求 id）。

**可能追问：**

- `toolContext` 和普通对话内容为什么必须分离？（避免模型当普通内容处理或泄露）
- 工具执行结果如何回到前端？（项目通过 `ToolResultHolder` 以 requestId 暂存，流结束时发 PARAM 事件）

### Q8：工具是怎么"让大模型知道"的？大模型又怎么"调用"工具？

**难度：困难**

**简要回答：**

本质是 **"大模型 ↔ 框架 ↔ 你的 Java 方法"的三方循环**。工具其实是大模型"提出调用请求"，框架代理执行，再把结果回传让它续写。

**第一步：让大模型"知道"有这些工具（注册 / 发现）**

1. 方法上打 `@Tool(description=...)`，参数用 `@ToolParam(description=...)` 说明；类上加 `@Component` 受 Spring 管理。
2. `SpringAIConfig` 用 `.defaultTools(courseTools, orderTools)` 把工具类交给 `ChatClient`。
3. Spring AI 启动时**反射扫描**带 `@Tool` 的方法，转成一份 **JSON Schema（工具说明书）**：函数名、参数名/类型、`description`。
4. schema 随每次请求一起发给大模型。**此刻模型只拿到"说明书"，没执行任何代码。**

**第二步：大模型"调用"（决定 + 框架代理执行）**

```
用户："帮我下单三门课，id 1、2、3"
  → [1] 请求发出：用户消息 + 工具 schema
  → [2] 大模型判定应调用 prePlaceOrder，返回结构化调用请求：
         { 函数名: "prePlaceOrder", 参数: { ids: [1,2,3] } }
  → [3] 框架拦截该请求，在注册表找到 OrderTools.prePlaceOrder 方法
  → [4] 框架注入 toolContext 并反射执行：prePlaceOrder([1,2,3], toolContext)
         （内部真实查库 / 调 Feign / 下单）
  → [5] 方法返回值作为"工具结果"消息回传给大模型
  → [6] 大模型基于结果生成最终回复："已为您预下单成功，共 ¥xxx …"
```

几个关键结论：

- "知道工具" = 收到 JSON schema；"调不调 / 传什么参"由模型根据对话内容决定。
- "不会真调你的代码" = 模型只发请求，框架反射执行，再回传结果。
- 每轮可能连续调多个工具（先查课程再下单），模型一步步看结果推进。
- **`@Tool` 的 `description` 写得好坏，直接决定模型会不会在合适时机调对工具**（写太泛会乱调，写太细会漏调）。
- 方法名会出现在发给模型的 schema 里，应取见名知义的英文名。

**可能追问：**

- 工具调用结果为什么还要回传模型一次？（让模型"看到结果"才能组织自然语言回复）
- 模型乱调/参数格式错误如何处理？（`description` 引导 + schema 约束；框架侧做参数解析校验）
- 一个请求里连续多次工具调用，框架如何串联？（多轮 tool call / tool response 往返）

## 五、会话记忆存储（回顾）

### Q9：改造前 `ChatMemory` 存在哪里？对话记录是怎么保存的？

**难度：中等**

**简要回答：**

对话记录**存在 Redis**。最终落库形态是一个 Redis List：key = `CHAT:{conversationId}`，value = 每条消息序列化后的 JSON。

**完整数据流（自底向上）：**

1. **存储层 `RedisChatMemoryRepository implements ChatMemoryRepository`**
   - `saveAll()`：`boundListOps(key)`，**先 `deleteByConversationId` 删旧 List，再对每条消息 `rightPush(JSON)`——全量覆盖写，不是增量 append**。
   - `findByConversationId()`：`range(0, -1)` 取出全部元素，再用 `MessageUtil.toMessage` 反序列化回 `Message`。
   - key 规则：前缀 `CHAT:` + `conversationId`。

2. **`conversationId` 怎么生成**：`ChatService.getConversationId(sessionId)` = `UserContext.getUser() + "_" + sessionId`，即"用户id_会话id"，隔离不同用户与会话。

3. **谁在背后自动读写**：`MessageChatMemoryAdvisor`（`SpringAIConfig` 里注册成默认 Advisor，内部持有 `ChatMemory` = `MessageWindowChatMemory`，默认 `maxMessages=100`）。
   - 请求前：用 `CONVERSATION_ID` 调 `findByConversationId()` 读出历史，拼进本次请求上下文（实现多轮记忆）；
   - 响应后：把 [历史 + 本轮提问 + 回答] 调 `saveAll()` 整段写回。
   - 所以业务代码只需 `.param(ChatMemory.CONVERSATION_ID, conversationId)`，不用手动调 repository。

4. **序列化细节**：`MessageUtil.toJson` 把 `Message`（System/User/Assistant/Tool 等）转成自定义 `MyMessage` 再转 JSON；**Assistant 消息额外把 `ToolResultHolder` 里的工具参数一并存进 JSON**，这样历史记录能还原当时下单/查课的参数（读取时用 `MyAssistantMessage` 还原）。中断时 `AbstractAgent.saveStopHistoryRecord` 兜底手动写一条。

**多智能体改造提醒：** 现有 key 只按 `userId_sessionId` 隔离，**路由智能体和专项智能体若共用同一 sessionId，会读到同一份历史**。若希望各智能体记忆隔离，要把 `AgentTypeEnum` 拼进 conversationId（如 `{type}_{userId}_{sessionId}`）；若希望切换智能体时上下文连贯，现状即可。

**可能追问：**

- `KEYS CHAT:*` 有什么风险？（大数据量阻塞，应改用 `SCAN`）——详见《AI对话项目面试复习.md》Q16
- 为什么 `saveAll` 要先删后写？（repository 接口约定传入的是全量消息，需保证幂等；代价是写放大）
- 新增消息类型时，`MessageUtil.toMessage` 的 `switch` 怎么扩展？

## 六、多态挂载与智能体分发

### Q10：`.advisors(advisor -> advisor.advisors(this.advisors()).params(this.advisorParams(sessionId, requestId)))` 是什么意思？怎么区分不同 Agent 挂载不同 Advisor？

**难度：困难**

**简要回答：**

这一行把"**挂哪些 Advisor**"和"**给 Advisor 传哪些参数**"都从硬编码改成调用 `this` 上的方法，由**运行时真正被调用的子类**决定结果。

拆解（注意两个 `advisor` 含义不同）：

```java
.advisors(           // ① 请求构建器，进入"配置本次请求 Advisor"模式
    advisor ->        // ② 形参其实是 AdvisorSpec 构建器（别被名字误导）
        advisor.advisors(this.advisors())        // ③ 把"本 Agent 声明的 Advisor 列表"挂上
               .params(this.advisorParams(sessionId, requestId)) // ④ 设置本次请求参数
)
```

- `this.advisors()`：**子类 override 的方法**，返回它要挂的 Advisor（多态动态绑定）。
- `this.advisorParams(...)`：给这批 Advisor 传 request 级参数。

**为什么能区分不同 Agent：** 因为 `getChatClientRequest` 写在父类，执行时 `this` 指向真正的子类对象，遇到 `this.advisors()` 会动态绑定到子类的实现。**同一套模板、不同的 `this`，挂载结果不同——完全靠子类各自 override，父类不需要 if/switch 判断类型。**

**区分不同 Agent 挂不同 Advisor 与 `getAgentType()` 的关系（两个层面，别混淆）：**

| 层面 | 手段 | 作用 |
|---|---|---|
| 路由层（选谁） | `getAgentType()` 返回 `AgentTypeEnum` | 路由智能体判断意图后，拿着类型从容器挑对应 Bean 并转发 |
| 能力层（装什么） | 子类 override 的 `advisors()` / `tools()` / `systemMessage()` | 决定这个 Agent 对话时挂哪些增强、带哪些工具 |

`AgentTypeEnum` 只用于"路由找到该找谁"；"挂不同 Advisor"靠子类多态。两者由同一个子类绑定在一起：`BuyAgent.getAgentType()==BUY` 且它的 `advisors()`/`tools()` 就是下单相关配置。

**子类写法示例：**

```java
// 知识讲解智能体：挂 RAG 检索
@Component
public class KnowledgeAgent extends AbstractAgent {
    private final Advisor qaAdvisor = QuestionAnswerAdvisor.builder(vectorStore)
            .searchRequest(SearchRequest.builder().similarityThreshold(0.6d).topK(6).build())
            .build();
    @Override public AgentTypeEnum getAgentType() { return AgentTypeEnum.KNOWLEDGE; }
    @Override public List<Advisor> advisors() { return List.of(qaAdvisor); }
}

// 课程购买智能体：不挂 RAG（下单靠 tools()），Advisor 可为空
@Component
public class BuyAgent extends AbstractAgent {
    @Override public AgentTypeEnum getAgentType() { return AgentTypeEnum.BUY; }
    @Override public List<Advisor> advisors() { return List.of(); }
    @Override public Object[] tools() { return new Object[]{ orderTools }; }
}
```

**`advisorParams` 是给谁传参：**

`AbstractAgent` 的默认实现返回 `Map.of(ChatMemory.CONVERSATION_ID, conversationId)`，给默认的 `MessageChatMemoryAdvisor` 用（所有 Agent 都需要，所以放父类）；某个 Agent 若要给自己专属 Advisor 传额外参数，就 override 并在 `super.advisorParams(...)` 基础上追加 key。

**两个留意点：**

1. lambda 形参 `advisor` 与 `this.advisors()` 同名易误读，其实前者是局部构建器 `AdvisorSpec`。
2. `defaultAdvisors`（日志 + 记忆）与会话级 `advisors()`（如 RAG）是**叠加关系**：记忆/日志对所有 Agent 生效，RAG 只对 `KnowledgeAgent` 生效——这正是多智能体的预期效果。

**可能追问：**

- 为什么不在父类里用 `switch (getAgentType())` 来决定挂什么？（违背开闭原则，每加一种智能体都要改父类；多态让扩展点收敛到子类）
- 如何从 Spring 容器按 `AgentTypeEnum` 取对应 Bean？（维护 `Map<AgentTypeEnum, Agent>` 注册表，或用带 `@Qualifier`/Bean 名约定 + 注入 `Map`）
- RAG 的 `QuestionAnswerAdvisor` 是每次重建还是复用？（每个请求重建有额外开销，可复用实例，但注意其内部状态与线程安全）

## 七、用户上下文与请求线程（UserContext / ThreadLocal）

> 本节由 `AbstractAgent.process()` 中的 `UserContext.getUser()` 引出，讲清用户身份在请求链路里是如何存取、并发下是否安全，以及为什么工具/异步边界要改用 `toolContext` 显式传参。涉及 `tj-common` 的 `UserContext`、`tj-auth-resource-sdk` 的拦截器与网关过滤器。

### Q11：`UserContext` 是从哪来的？是"每个用户维护一个 UserContext"吗？

**难度：中等**

**简要回答：**

`UserContext` 是 **`tj-common` 模块的静态工具类**，底层就是一个 `ThreadLocal<Long>`：

```java
public class UserContext {
    private static final ThreadLocal<Long> TL = new ThreadLocal<>();  // 每个线程一份拷贝
    public static void setUser(Long userId) { TL.set(userId); }
    public static Long getUser()             { return TL.get(); }
    public static void removeUser()          { TL.remove(); }
}
```

所以准确说法是：**全局只有一份 `UserContext`（不需要、也不能 `new`，方法全是 `static`），但内部 `ThreadLocal` 让"每个线程各自持有一份独立的 userId"——不是每个用户一个对象，而是每个线程一个"用户槽位"。**

`ThreadLocal` 的语义：同一个变量在每个线程里各存一份拷贝，线程 A `setUser(100)` 只有线程 A 能读到 100，线程 B 读到的是 `null`，互不干扰，天然线程隔离（不需要加锁）。

**用户是谁放进去的？（完整身份链路）**

```
浏览器 ── JWT ──► 网关 AccountAuthFilter（Spring Cloud Gateway）
                   │ 解析 JWT → 把 userId 写进转发请求头 user-id（它自己不 setUserContext）
                   ▼
              tj-aigc 服务（Spring MVC）
                   │ UserInfoInterceptor.preHandle（order=0）
                   │    UserContext.setUser(Long.valueOf(request.getHeader(USER_HEADER)))
                   │ LoginAuthInterceptor（order=1）校验是否登录
                   ▼
              Controller → Service → AbstractAgent.process/processStream
                   │ 同线程可 UserContext.getUser() 取到 userId
                   ▼
              UserInfoInterceptor.afterCompletion → UserContext.removeUser()  ← 兜底清理
```

- **网关 `AccountAuthFilter`**：`parseToken` 后 `header(USER_HEADER, userId)`，只负责"解析 + 下发请求头"，不做 set。
- **`UserInfoInterceptor`（order=0）**：真正 `setUser`，从网关传来的请求头取 userId。
- **`LoginAuthInterceptor`（order=1）**：只校验 `UserContext.getUser() != null`，不负责 set。
- 注册顺序与路径规则在 `ResourceInterceptorConfiguration`。
- **Feign 调用下游**：`FeignRelayUserInterceptor`（Feign 的 `RequestInterceptor`）在发请求前同步读 `UserContext` 写入请求头，下游服务再由它的 `UserInfoInterceptor` `setUser`，实现身份跨服务延续。

**可能追问：**

- 为什么 `UserInfoInterceptor` 要在 `afterCompletion` 里 `removeUser()`？（防线程池复用串号，见 Q12）
- 网关为什么不直接调 `UserContext.setUser`？（网关是 WebFlux 应用、且与业务服务不同 JVM，只能通过请求头传递）
- `UserContext.getUser()` 取到 `null` 说明什么？（未登录 / 入口没 set / 跨了线程）

### Q12：并发时两个用户同时调用 `process()` 会怎样？会串号吗？

**难度：中等**

**简要回答：**

**本项目是 Spring MVC（`spring-boot-starter-web`）阻塞模型，一请求一线程，两个并发请求落在两个 Tomcat 线程上，`ThreadLocal` 天然隔离，各自读到各自的 userId，不会串号。**

**但首先要澄清一个前提：本项目不是纯 WebFlux。** 依赖里只有 `spring-boot-starter-web`；Controller 返回 `Flux`、配 SSE 只是"以流式响应体写出"，底层仍是 Servlet 阻塞模型，不是 Reactor 的少数 event-loop 线程交替处理所有请求。所以 `process()` / `processStream()` 订阅阶段同步执行的 `getUser()` 就是处理该请求的同一线程，可靠。

**ThreadLocal 真正需要防的两个坑：**

| 坑 | 后果 | 本项目的对策 |
|---|---|---|
| ① 线程池复用 + 漏 `removeUser()` | Tomcat 线程被复用，下一个请求没 set 时可能读到上一个用户的 id → 串号 | `UserInfoInterceptor.afterCompletion` 里 `removeUser()` 兜底清理 ✔ |
| ② 跨线程 / 异步边界（`@Async`、响应式回调） | `ThreadLocal` 只认当前线程，线程一切换就读不到 | 不在异步处依赖 `UserContext`，改用显式传参 |

**为什么工具里要像 `OrderTools` 那样走 `toolContext` 而不是 `UserContext.getUser()`：** 工具往往在流式异步回调深处被调用，ThreadLocal 可能已丢；`OrderTools.prePlaceOrder` 从 `toolContext.get(USER_ID)` 取出后 `UserContext.setUser(...)` 手动塞回当前线程，是为了让随后的 Feign 调用（`FeignRelayUserInterceptor` 读当前线程）能带上身份。这正是"**在 ThreadLocal 可能失效的异步段，用显式传参兜底**"的典型做法，多智能体改造时应沿用此原则。

**阻塞式 vs 响应式的本质区别：**

| | 阻塞式（本项目，spring-boot-starter-web） | 响应式（WebFlux / Reactor Netty） |
|---|---|---|
| 线程模型 | 每个请求独占一个 Tomcat 线程，全程不变 | 少量 event-loop 线程并发交替处理所有请求 |
| ThreadLocal | 请求内可靠 | 会因线程切换丢失，需用 Reactor Context / 显式传参 |
| 该项目为何还能返回 Flux | MVC 支持把 Flux 作为流式响应体写出，底层仍是 Servlet 阻塞模型 | — |

**可能追问：**

- `ThreadLocal` 的内存泄漏风险？（线程池中线程长期存活、key 是弱引用 value 是强引用，务必 `remove`）
- 网关用 WebFlux，为什么它反而不存 `UserContext`？（跨 JVM 无法共享，只能请求头传递；这也解释了网关与业务服务的分工）
- 多智能体改造时，`process()` 被路由层转发后身份会丢吗？（同一请求内转发仍是同线程则不会；若跨线程/异步编排，就把 userId 提前取出随上下文传递）

## 八、processStream 执行链路与数据流转

> 本节深入 `AbstractAgent.processStream` 这条流式对话的核心流水线，讲清响应式算子的职责、停止/中断机制、以及 `ToolResultHolder` 与 `advisorParams` 这两个"请求级数据"是什么时候写入、怎么被消费的。

### Q13：`processStream` 是怎么工作的？（流式对话的完整响应式链路）

**难度：困难**

**简要回答：**

`processStream` 把一次流式对话组织成一条响应式流水线：先由子类装配好请求（系统提示词/Advisor/工具），再用一系列 Reactor 算子实现"生成状态标记 → 可被 stop 协作式取消 → 中断时保存已生成内容 → 结束后回传工具参数 → 发结束标记"。核心代码：

```java
return this.getChatClientRequest(sessionId, requestId, question)
        .stream().chatResponse()                        // 真正以流式发请求 → Flux<ChatResponse>
        .doFirst(() -> GENERATE_STATUS.put(sessionId, true))      // 订阅即置"生成中"
        .doOnError(t -> GENERATE_STATUS.remove(sessionId))        // 异常清标记
        .doOnComplete(() -> GENERATE_STATUS.remove(sessionId))    // 正常完成清标记
        .doOnCancel(() -> saveStopHistoryRecord(conversationId, outputBuilder.toString())) // 中断兜底
        .takeWhile(r -> GENERATE_STATUS.getOrDefault(sessionId, false))  // 停止机制开关
        .map(chatResponse -> { ... 累积 outputBuilder；结束块登记 messageId→requestId；返回 DATA 事件 ... })
        .concatWith(Flux.defer(() -> { ... 取 ToolResultHolder → 发 PARAM + STOP_EVENT ... }));
```

**两个重要前提（先理解再读代码）：**

1. **懒执行**：方法头（取 userId、生成 requestId）调用时立即执行；从 `.stream()` 起的算子链只是"搭管道"，真正发请求要等**有人订阅**（Controller 把 Flux 返回后由 Web 框架 subscribe）。
2. **协作式取消**：停止不是"掐断"，而是通过 `takeWhile` 判断一个标志位来"优雅终止"。`stop(sessionId)` 只是 `GENERATE_STATUS.remove(sessionId)`，下次分片到达 `takeWhile` 时判定为 false，主流 `onComplete` 并 cancel 上游。

**逐算子职责：**

| 算子 | 执行时机 | 作用 |
|---|---|---|
| 方法头同步段 | 调用时 | 取 userId / 生成 requestId / 建 `outputBuilder` / 算 conversationId / `@Async` 更新会话时间 |
| `.stream().chatResponse()` | 订阅后 | 真正向大模型发流式请求 |
| `doFirst` | 订阅时（早于任何数据） | 置 `GENERATE_STATUS[sessionId]=true`，允许后续被 stop |
| `doOnError` / `doOnComplete` | 出错 / 正常结束 | 清标记，避免 Map 残留脏状态 |
| `takeWhile` | 每个分片到达时 | 标志还在→放行；被 stop 后标志没了→结束主流 + cancel 上游（**核心停止机制**） |
| `doOnCancel` | 被取消时 | 把 `outputBuilder` 已累积文本写回 ChatMemory（Redis），避免中断丢内容 |
| `map` | 每个分片 | 累积文本、模型说完一句时登记 `messageId→requestId`、包装成 `DATA` 事件推前端 |
| `concatWith(Flux.defer(...))` | 主流结束后 | 取工具结果发 `PARAM`；无论有无都发 `STOP_EVENT` 收尾 |

**为什么结尾用 `Flux.defer`：** 把读取逻辑延迟到"订阅时"才执行——若在组装管道阶段就执行 `ToolResultHolder.get(requestId)`，此时工具还没被调用，必然拿到空 Map。`defer` 保证它发生在整个流跑完之后。

**几个值得注意的点：**

- **生成状态从 Redis 换成了本地 `ConcurrentHashMap`**（改造前 `ChatServiceImpl` 用 Redis Hash）。优点快、零网络；代价是 stop 只能停"当前实例"上的流——多实例部署时请求在 A、stop 打到 B 会停不掉。单机够用，分布式需换 Redis（代码注释已预留方向）。
- `outputBuilder` 被 `map`（写）与 `doOnCancel`（读）共享。阻塞式 MVC 下同线程驱动安全；若将来纯 WebFlux 化、分片并发到达，`StringBuilder` 非线程安全需换。
- 停止是"下一个分片到达时"才生效，模型在生成长分片时会有感知延迟；要"立即断流"需拿到底层订阅句柄 `dispose()`。

**可能追问：**

- `takeWhile` 与 `takeUntil` 的区别？（前者遇到 false 即停并结束流，后者是"取到满足条件为止"）
- 为什么中断时还要手动存历史？（被取消时 `MessageChatMemoryAdvisor` 的"响应后写回"可能没机会完整执行，需兜底）
- 本地 Map 与 Redis 两种停止方案各自适用什么场景？（见上"值得注意的点"）

### Q14：`ToolResultHolder` 里的内容是什么时候放进去的？为什么主链路里看不到 put？

**难度：中等**

**简要回答：**

因为在**工具方法内部**写入，不在 `processStream` 主链路里。`ToolResultHolder` 是进程内静态 `ConcurrentHashMap<String, Map<String,Object>>`（requestId → 字段名 → 工具结果），服务于"一次请求从发出到结束"的短暂生命周期。

**完整的写入 / 读取 / 桥接共三处：**

| 位置 | 何时执行 | 动作 |
|---|---|---|
| **写入①** 工具方法内（`OrderTools` / `CourseTools`） | 大模型决定调用工具、框架执行工具方法时 | `put(requestId, 字段名, 工具结果)` |
| **桥②** `processStream.map`（finishReason==STOP 的分片） | 模型每说完一句话的最后一个分片 | `put(messageId, REQUEST_ID, requestId)` |
| **读取③** `processStream.concatWith` 末尾 | 整个流结束 | `get(requestId)` → 发 PARAM；取完 `remove` |
| **读取④** `MessageUtil.toJson` | 保存会话历史时 | 经 messageId 反查 requestId、再取 params，并进历史 JSON |

**写入①（以 `OrderTools.prePlaceOrder` 为例）：**

```java
@Tool(description = "...")
public PrePlaceOrder prePlaceOrder(List<Number> ids, ToolContext toolContext) {
    ...
    var requestId = Convert.toStr(toolContext.getContext().get(Constant.REQUEST_ID)); // 关键：从 toolContext 拿回 requestId
    ToolResultHolder.put(requestId, "prePlaceOrder", prePlaceOrder);  // ★ 写入发生在工具被调用时
    return prePlaceOrder;
}
```

工具方法必须有 requestId 才能 put，而它自己不生成——这就是 `toolContext` 的意义：`getChatClientRequest` 通过 `.toolContext(this.toolContext(sessionId, requestId))` 把 requestId 注入，工具执行时从 `toolContext.get(REQUEST_ID)` 取回，从而与 `processStream` 生成的 requestId **是同一个**，靠它把"流"和"工具结果"关联。

**桥② 是给"历史记录"搭桥：** 模型说完一句话，把 `messageId → requestId` 记入 Holder。之后 `MessageUtil.toJson` 存历史时，靠 messageId 反查到 requestId、再反查该 requestId 下存过的工具参数，一并写进这条 Assistant 消息的 JSON——这样翻历史能看到当时下单/查课用的结构化参数。

**为什么用内存 Map + 及时 remove：** 只服务一次请求的短暂生命周期，不需要落库或跨实例，静态内存表足够快；真正的历史由读取④落进 Redis。

**可能追问：**

- 为什么 put 要下沉到工具方法而不是主链路？（工具最清楚自己产出的字段名与归属 requestId；主链路只负责流结束时统一取出）
- 读取④为什么要"先取 messageId 再取 requestId"？（历史存储只有 messageId 可定位消息，需经桥②两级反查）
- 中断时（`doOnCancel`）工具已 put、但流没走到 concatWith 就结束，那个 requestId 会残留吗？（会——这是现存的一个边界缺口，可评估在取消兜底里一并清理）

### Q15：`advisorParams` 是做什么的？返回的 Map 怎么生效？

**难度：中等**

**简要回答：**

`advisorParams(sessionId, requestId)` 返回的是**"本次请求级"的 Advisor 上下文参数**。Spring AI 会把这份 Map 合并进"本次模型调用"的请求上下文，链路上每个 Advisor 执行时按 key 从上下文中取值。你这里的 `CONVERSATION_ID` 就是给记忆 Advisor 定位"这次对话属于哪个会话"的：

```java
@Override
public Map<String, Object> advisorParams(String sessionId, String requestId) {
    var conversationId = ChatService.getConversationId(sessionId);   // "userId_sessionId"
    return Map.of(ChatMemory.CONVERSATION_ID, conversationId);
}
```

**生效链路（对照 `SpringAIConfig`）：**

```
本次请求发出
  → 上下文被放入 { CONVERSATION_ID: "100_abc123" }          ← advisorParams 的产物
  → Advisor 链执行，轮到 MessageChatMemoryAdvisor（默认 Advisor）
  → 它从上下文 get(CONVERSATION_ID) → "100_abc123"
  → chatMemory.findByConversationId("100_abc123")
       → RedisChatMemoryRepository 读 CHAT:100_abc123 这条 List
  → 历史拼进请求；响应结束后 saveAll 写回同一条 List
```

所以 `MessageChatMemoryAdvisor` 正是靠这个参数才知道"去哪读写哪份记忆"。缺失或传错会导致读不到历史或会话记忆错乱。

**三层概念别混淆：**

| 对象 | 是什么 | 谁提供 |
|---|---|---|
| `ChatClient` 的 defaultAdvisors | 全局默认 Advisor（日志、记忆） | `SpringAIConfig`，所有请求都有 |
| `this.advisors()` | 本次请求追加的 Advisor（如 RAG） | 当前 Agent 决定 |
| `advisorParams()` | 给上面这些 Advisor 用的请求级参数 | 当前 Agent 决定 |

一句话：**`advisors()` 决定"挂谁"，`advisorParams()` 决定"这些 Advisor 干活时看哪些参数"。** 不是每个参数都被每个 Advisor 用——各 Advisor 只从上下文取它认识的那些 key：`CONVERSATION_ID` 被记忆 Advisor 消费；RAG Advisor 读的是用户消息文本、检索参数在构造时配好，不读它；日志 Advisor 也不读。这正是"用 Map 统一传参、各取所需"的意图。

**与另外两个"参数方法"的区别：**

| 方法 | 参数给谁 | 作用范围 |
|---|---|---|
| `systemMessageParams()` | 系统提示词模板里的 `{{占位符}}` | 只影响 system 文本渲染 |
| `advisorParams()` | 本次请求链路上的 Advisor | 影响 Advisor 行为（记忆读写、检索等） |
| `toolContext()` | 被调用的工具方法 | 工具执行时取用（如 USER_ID、REQUEST_ID） |

三者都是**请求级瞬时数据**，不落库、不跨请求，只是消费方不同。

**可能追问：**

- 早期写法 `.param(CONVERSATION_ID, conversationId)` 与现在的 `.params(map)` 有何区别？（同一请求级参数，单 key vs 统一 Map）
- 路由智能体与专项智能体共用同一 sessionId 时，`CONVERSATION_ID` 怎么生成才能共享同一份记忆？（按 `userId_sessionId` 生成即可共享；若要隔离需把 AgentTypeEnum 拼进去，见 Q9）
- 想给某个 Advisor 传自定义参数该怎么做？（override `advisorParams`，在 `super.advisorParams(...)` 结果上追加自己的 key）

## 九、改造前后对照（口述参考）

> 原项目 `ChatServiceImpl` 把"系统提示词（Nacos）、RAG 检索 Advisor、课程/下单工具、REQUEST_ID 与 USER_ID 的 toolContext、Redis 生成状态"全部硬编码在同一个聊天流程中。改造后，公共流程收敛到 `AbstractAgent`（`process` 同步、`processStream` 流式、中断兜底、请求装配骨架），差异点由 `systemMessage()`、`tools()`、`advisors()`、`toolContext()` 等方法在子类各自声明；`AgentTypeEnum` 用类型标识不同智能体，路由智能体负责判断用户意图并从容器选取对应专项智能体转发，实现"一个智能体一套配置、按需启用工具与知识库检索"。
>

## 十、容易答错的细节

- `name()` 来自隐式父类 `java.lang.Enum`；枚举默认 `toString()` 就是返回 `name`。
- 枚举构造器默认 `private`，外部不能 `new`，常量是单例。
- `process` = `.call()` 同步整包；`processStream` = `.stream()` 流式逐块。
- `.system/.user/.advisors/.tools/.toolContext` 都只是"拼请求"，`.call()` / `.stream()` 才真正发送。
- `toolContext` 给工具执行方法看，**不发给大模型、不进工具 schema**。
- 大模型"知道"工具 = 收到 JSON schema 说明书；"调用" = 框架反射执行再回传结果。
- 对话记录存 Redis List，key `CHAT:{userId}_{sessionId}`；`saveAll` 是**先删后全量重写**。
- `AbstractAgent` 是模板方法模式：公共逻辑父类写死，差异点（`systemMessage/tools/advisors/...`）子类 override。
- 区分不同 Agent 挂不同 Advisor 靠**运行时多态 + 子类各自 override**，不是父类里 switch 类型；`AgentTypeEnum` 只用于路由分发。
- 同一会话下路由与专项智能体会共享同一份历史记忆（当前 conversationId 不含智能体类型）。
- `UserContext` 是 `tj-common` 的静态工具类，底层是 `ThreadLocal<Long>`；**不是每用户一个对象，而是每线程一个槽位**。
- setUser 由 `UserInfoInterceptor.preHandle`（order=0）做，removeUser 由它的 `afterCompletion` 兜底；`LoginAuthInterceptor` 只校验、网关只下发请求头。
- 本项目是 Spring MVC（阻塞式）非纯 WebFlux，一请求一线程，`ThreadLocal` 请求内可靠；但线程池复用漏 remove 会串号，异步/Feign 边界会丢值。
- 工具方法在异步回调里取不到 `UserContext` 时，走 `toolContext` 显式传 `USER_ID`（`OrderTools` 的做法），必要时再手动 `UserContext.setUser(...)` 供 Feign 读取。
- `processStream` 是**懒执行流**：搭管道不跑，订阅才发请求；末尾 `Flux.defer` 让读取逻辑延迟到整个流结束后执行。
- 停止是**协作式取消**：`stop()` 删 `GENERATE_STATUS` 标志，等下一个分片到 `takeWhile` 才终止；不是立即断流。
- 生成状态改造后是**本地 `ConcurrentHashMap`**，单机够用；多实例部署 stop 可能停不掉，需换 Redis。
- `ToolResultHolder` 的写入在**工具方法内部**（工具执行时 put），不在主链路；主链路只在流结束时 get + remove。
- `toolContext` 里的 `REQUEST_ID` 是工具拿到 requestId 的唯一通道，`processStream` 生成的 requestId 靠它与工具结果关联。
- `advisorParams()` 返回的 Map 合并进**本次请求的 Advisor 上下文**；`MessageChatMemoryAdvisor` 按 `CONVERSATION_ID` 定位 Redis 记忆，各 Advisor 只取自己认识的 key。
- `advisors()` 决定挂谁，`advisorParams()` 决定这些 Advisor 看哪些参数，两者配合：默认 Advisor（记忆/日志）人人有，会话级 `advisors()`（如 RAG）只对该 Agent 生效。

## 十一、Spring 依赖注入与 Bean 装配

> 本节回答面试中关于多智能体类"为什么没写 @Autowired 也能注入"的疑问，本质是 Lombok 生成构造器 + Spring 隐式构造器注入两件事的组合。

### Q16：BuyAgent / RecommendAgent 里 `private final SystemPromptConfig systemPromptConfig;` 没写 @Autowired，为什么能注入成功？

**难度：基础**

**简要回答：**

能注入不是字段上有什么魔法，而是三个条件叠加：类被 `@Component` 注册为 Spring Bean；Lombok 的 `@RequiredArgsConstructor` 为 final 字段生成构造器；Spring 对"只有一个构造器的 Bean"会自动做构造器注入（4.3 起无需 `@Autowired`）。

对照代码（`BuyAgent`）：

```java
@Component
@RequiredArgsConstructor          // Lombok：为 final / @NonNull 字段生成全参构造器
public class BuyAgent extends AbstractAgent {
    private final SystemPromptConfig systemPromptConfig;   // 唯一的 final 字段 → 唯一的构造器参数
}
```

1. **Lombok 编译期生成**：`public BuyAgent(SystemPromptConfig systemPromptConfig) {...}`。`final` 恰好要求"构造时必须赋值、之后不可变"，驱动它进入构造器。
2. **Spring 自动注入**：BuyAgent 是 Bean，且只有这一个构造器 → 容器自动从容器取 `SystemPromptConfig` 传入（隐式构造器注入，等价于在该构造器上标 `@Autowired`）。
3. **SystemPromptConfig 能被取到**：它本身标了 `@Configuration`（`SystemPromptConfig.java`），是容器里的 Bean。

**项目落地：**

`RecommendAgent` / `BuyAgent` / `RouteAgent` 及 `ChatServiceImpl` 等服务层普遍采用「`@RequiredArgsConstructor` + final 字段」这一**构造器注入**风格；而父类 `AbstractAgent` 不这么写，它对 `chatClient` / `chatMemory` 用字段级 `@Resource` 注入——因为父类不是具体 Bean、没有自建构造器，且这些依赖对所有子类通用。两条路都是把依赖交给 Spring 容器管理，差别是"隐式构造器注入"还是"按类型字段注入"。

**可能追问：**

- 若一个类有多个构造器，Spring 怎么选？（需在某个构造器上显式标 `@Autowired` 指明要注入的那个）
- 为什么官方更推荐构造器注入而非字段注入？（依赖显式、`final` 保证不可变、单测好构造；字段注入让依赖隐式，易出现"Bean 建好但字段没注入"的坑）
- 构造器注入遇到循环依赖会怎样？（启动期就暴露、无法靠延迟解决；本项目 `allow-circular-references: true` 是为兼容既有循环引用，应尽量重构避免）
- `@RequiredArgsConstructor` 到底把哪些字段收进构造器？（`final` 字段 + 标了 `@NonNull` 的字段）

## 十二、多智能体的本地测试与运行前提

> 本节由 `RouteAgentTest` / `RecommendAgentTest` 两个 `@SpringBootTest` 引出：为什么 IDEA 里右键就能跑、它们真正依赖哪些外部中间件、各自"跑过"的条件有何不同。

### Q17：这些 @SpringBootTest 为什么在 IDEA 里右键就能跑，不需要先 `mvn install` 把上游模块装进本地仓库？

**难度：基础**

**简要回答：**

因为 IDEA 把根 `pom.xml` 当成**同一个 reactor（多模块工程）**处理。`tj-aigc` 依赖的 `tj-common`、`tj-api`、`tj-auth-resource-sdk` 都在 reactor 的 `<modules>` 里，IDEA 右键运行测试时会先按依赖自动编译这些模块，把各自的 `target/classes` 编译产物直接加进 classpath，**不需要它们被 install 成 jar 放进 `~/.m2`**。

需要区分两条构建路径：

| 场景 | 上游模块怎么来 | 是否依赖本地仓库 |
|---|---|---|
| IDEA 运行（右键 / Run） | reactor 内模块实时编译，class 直接进 classpath | 否 |
| 命令行 `mvn test -pl tj-aigc`（不带 `-am`） | 去本地仓库找 tj-common / tj-api 等 jar | 是，缺则报错 |

**项目落地：** 本项目从未单独把 `tj-common` 等 install 进本地仓库，但 IDEA 里测试 / 启动一直正常，就是这个原因。真正需要 `mvn install -pl 上游模块 -am` 的典型场景是：脱离 reactor 单独构建某模块、CI 分段打包、命令行只测单个模块且不想连带编译上游。

**可能追问：**

- `-am`（`--also-make`）的作用？（构建指定模块时，连同它依赖的 reactor 模块一起构建）
- 命令行想跑 tj-aigc 测试又不想污染本地仓库，怎么办？（`mvn test -pl tj-aigc -am`，把上游模块一起带进来构建）

### Q18：RouteAgentTest / RecommendAgentTest 能"跑过"的前提是什么？两个测试有何不同？

**难度：中等**

**简要回答：**

两者都是 `@SpringBootTest`，会**启动完整 Spring 容器**并**真实调用大模型**。所以"通过前提"分两层：**容器能启动（外部中间件都连得上）** + **被测方法执行不抛异常 / 断言通过**。

先看被测 Agent 的差别（决定它对环境的依赖）：

| 测试 | 调用方法 | 有无断言 | 走 RAG/ES？ | 走工具？ |
|---|---|---|---|---|
| RouteAgentTest | `process`（同步 `.call()`） | 有：`Assert.equals(输出, 枚举代号)` | 否（未覆写 `advisors`） | 否（`tools` 为空） |
| RecommendAgentTest | `processStream`（流式 + `Thread.sleep(100s)`） | 无：只 subscribe + 打印 | 是（`advisors` 挂了 QuestionAnswerAdvisor） | 是（`tools=CourseTools`，模型决定才调） |

**容器要能启动所需的外部依赖（缺一个基本就红 / 起不来）：**

| 依赖 | 作用 | 缺失后果 |
|---|---|---|
| Nacos | 读 `aigc-service.yaml` 与 route/recommend 等系统提示词 txt | 上下文加载失败 / 提示词为 null |
| MySQL | 会话更新查询（`ChatSessionServiceImpl.update`） | 上下文加载失败 |
| Redis | 会话记忆 + 生成状态 | 上下文加载失败 / 运行报错 |
| Elasticsearch | `VectorStore`（RecommendAgent 构造器直接注入） | 上下文加载失败（ES 不可达常导致启动即失败） |
| DashScope + 联网 | 真实对话 / 向量化 | 运行报错 |
| tj-course 服务（Feign） | 仅当模型真调 `queryCourseById` | 不调用则不影响 |

**两个测试各自特点：**

- **RouteAgentTest 有断言但链路最简**：路由 Agent 不查 ES、不打工具，最小依赖更低；脆弱点在**断言是精确字符串等于**——路由模型输出的文本必须与 `AgentTypeEnum` 的 `agentName` 完全一致，多了换行 / 标点 / 语气词就会失败。这属于"模型输出稳定性"问题，不是功能 bug。
- **RecommendAgentTest 无断言，跑完不抛异常即通过**：但链路真挂 RAG（查 ES）+ 真调模型 + 可能调 Feign；且用写死的 `Thread.sleep(100000)` 阻塞主线程等异步流（不够优雅，跑完还得手动等/停）。

**可能追问：**

- 为什么"容器能启动"就隐含 Nacos/MySQL/Redis/ES 必须可达？（`@SpringBootTest` 加载完整 context，Bean 装配阶段就要连这些）
- 想不依赖外部中间件 / 省钱地测，怎么做？（用 `@MockBean` 替换 ChatClient / VectorStore，或 Mockito mock；但那测不到真实路由与检索效果）
- RecommendAgentTest 为什么订阅前要先 `UserContext.setUser(123L)`？（`processStream` 里 `UserContext.getUser()` 要拿到值；测试线程上没有网关拦截器替它 set，不 set 就是 null）
- RouteAgentTest 没 set user 却不报错，为什么？（`getUser()` 为 null 时 `update` 查不到会话记录直接 return，不抛异常）

## 十三、RAG 检索在多智能体中的按需挂载

> 本节把"知识检索"从改造前"每次聊天无条件全做"的写法，对比改造后"由子类声明是否挂载"的差异点设计。

### Q19：多智能体里"RAG 检索按需启用"是怎么做的？和改造前有什么不同？

**难度：中等**

**简要回答：**

靠 Agent 接口的差异点方法 `advisors()`。父类 `AbstractAgent` 未覆写时走 `Agent` 接口的默认实现——返回空列表（`Agent.java` 的 `default List<Advisor> advisors() { return List.of(); }`），所以子类不覆写＝不检索。`RecommendAgent` 覆写了 `advisors()`，返回一个 `QuestionAnswerAdvisor`，于是只有它（以及将来同样覆写的 KnowledgeAgent）会走 RAG：

```java
@Override
public List<Advisor> advisors() {
    var qaAdvisor = QuestionAnswerAdvisor.builder(this.vectorStore)
            .searchRequest(SearchRequest.builder().similarityThreshold(0.6d).topK(6).build())
            .build();
    return List.of(qaAdvisor);
}
```

对比改造前 `ChatServiceImpl.chat()`：它**每次请求都无条件** `new` 一个 `qaAdvisor` 并追加给所有聊天（代码里留有 TODO——"所有请求都会执行 RAG 检索，需按需启用、复用 Advisor 实例"）。改造后，把"是否检索、检索参数"下沉为子类声明的能力，`AbstractAgent.getChatClientRequest` 统一通过 `this.advisors()` 挂载（多态动态绑定），从而做到推荐/知识类挂 RAG、购买/路由类不挂——即"一个智能体一套配置，按需启用工具与知识库检索"。

**项目落地与注意点：**

- `RecommendAgent` 自己注入 `VectorStore`，在 `advisors()` 里构造检索器；`RouteAgent` / `BuyAgent` 不覆写 → 不检索。
- 该 Advisor 与全局默认 Advisor（记忆 / 日志）是**叠加**关系：默认的人人有，RAG 只对覆写者生效。
- 目前 `advisors()` 每次调用都新建 `QuestionAnswerAdvisor`（与改造前同样的问题）；更优做法是把 Advisor 做成字段级复用同一个实例，避免每次请求的构建开销。
- 与 RAG 配套的 `vectorStore` 数据来自 `EmbeddingController` 的知识入库接口（`POST /embedding`），即"灌进去什么，检索时才能召回什么"。

**可能追问：**

- `QuestionAnswerAdvisor` 在请求链路里做什么？（在 `before` 阶段拿用户问题对 VectorStore 做相似度检索，把命中文档按上下文模板拼进请求，引导模型"只依据上下文回答"）
- 怎么让某 Agent 既有 RAG 又要自定义 Advisor 参数？（override `advisors()` 返回组合列表；必要时再 override `advisorParams()` 追加参数）
- 为什么 RouteAgent 不需要 RAG？（它只做意图分发，期望输出是类型代号，不需要知识上下文）

## 十四、对话记忆的分层架构与 Redis 落库

> 本节把多智能体的"会话记忆"拆成一条接口/实现/仓库的层级链：`ChatMemory`（门面接口）→ `MessageWindowChatMemory`（窗口实现，管条数上限）→ `ChatMemoryRepository`（底层存储契约）→ `RedisChatMemoryRepository`（真正落 Redis）。与第五节 Q9（存什么、key 规则、序列化）配套阅读，本节侧重"谁调用谁、各自管什么"。

### Q20：`ChatMemory`、`MessageWindowChatMemory`、`RedisChatMemoryRepository` 之间是什么关系？

**难度：中等**

**简要回答：**

三者是"门面接口 → 窗口实现 → 底层 Redis 仓库"的三层结构，逐层持有下层：

```
MessageChatMemoryAdvisor(调用时机)      —— Spring AI 内置 Advisor，before 读 / after 写
        │
        ▼
ChatMemory(接口)                       —— 高层门面，定义 get / add / clear
        ▲  实际对象
MessageWindowChatMemory(窗口实现)       —— 管"窗口"：最多保留 maxMessages 条，超出截断
        │  （内部持有一个 ChatMemoryRepository）
        ▼
ChatMemoryRepository(接口)             —— 底层存储契约，定义 findByConversationId / saveAll / delete
        ▲  实际对象
RedisChatMemoryRepository(仓库实现)     —— 真正碰 Redis：Message ↔ JSON、List 读写、删 key
```

**装配链（`SpringAIConfig` 三个 Bean 逐层套娃）：**

```java
// 最底层：Redis 仓库（实现 ChatMemoryRepository + MyChatMemoryRepository 两个接口）
@Bean RedisChatMemoryRepository redisChatMemoryRepository() { return new RedisChatMemoryRepository(); }

// 中间层：ChatMemory 接口，实现是 MessageWindowChatMemory，内部注入上面的仓库
@Bean ChatMemory chatMemory(ChatMemoryRepository chatMemoryRepository) {   // 注入 RedisChatMemoryRepository
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(chatMemoryRepository)
            .maxMessages(this.maxMessages)   // 默认 100 条窗口
            .build();
}

// 最上层：Advisor，注入 ChatMemory，在 before/after 里驱动读写
@Bean Advisor messageChatMemoryAdvisor(ChatMemory chatMemory) {             // 注入 MessageWindowChatMemory
    return MessageChatMemoryAdvisor.builder(chatMemory).build();
}
```

依赖注入方向是 **Advisor → ChatMemory(窗口) → ChatMemoryRepository(Redis)**，链上最底层对象就是 `RedisChatMemoryRepository`。

**各自职责边界：**

| 组件 | 角色 | 只管什么 | 不管什么 |
|---|---|---|---|
| `ChatMemory` | 接口 / 门面 | 高层语义：`get` 读历史、`add` 追加、`clear` 清空 | 不知道 Redis、不知道序列化、不做条数裁剪 |
| `MessageWindowChatMemory` | 窗口实现 | **消息条数上限**：读回 → 追加 → 超 `maxMessages` 截断只留最近 N 条 | 不知道存哪里、怎么序列化 |
| `ChatMemoryRepository` | 底层契约接口 | 定义存储操作：`findByConversationId` / `saveAll` / `deleteByConversationId` | 不做窗口、不关心多轮语义 |
| `RedisChatMemoryRepository` | 仓库实现 | 真正碰 Redis：`MessageUtil` 序列化、List 读写、删除 key | 不做窗口裁剪 |

一句话：**`MessageWindowChatMemory` 决定"内存里留多少条"，`RedisChatMemoryRepository` 决定"具体放哪、怎么放"，`ChatMemory` 只是把前者包装成统一入口。**

**一次对话如何协作（结合反编译确认的内部逻辑）：**

1. 请求前 —— `MessageChatMemoryAdvisor.before()` 调 `chatMemory.get(conversationId)`
   → `MessageWindowChatMemory.get()` 转调 `findByConversationId()` → 读 Redis List `CHAT:{conversationId}` → 反序列化成 `Message` → 拼进请求发给大模型。
2. 响应后 —— `after()` 调 `chatMemory.add(conversationId, [本轮问题+回复])`
   → `MessageWindowChatMemory.add()` 内部（反编译）：先 `findByConversationId()` 读回当前全部 → 追加新消息 → **按 `maxMessages` 截断** → 再 `saveAll()` 全量写回。
3. `saveAll()` 落到 `RedisChatMemoryRepository.saveAll()`：先删旧 List，再逐条 `rightPush` 全量重写（先删后写，保证幂等，代价是写放大）。

由此得到一个易考点：**窗口裁剪发生在 `MessageWindowChatMemory`，全量重写发生在 `RedisChatMemoryRepository`**——先内存截断到 ≤100 条再整段写回，所以 Redis 里永远只留最近 100 条。

**与本项目"多智能体 + 接口隔离"的结合：**

`RedisChatMemoryRepository` 同时实现两个接口——Spring AI 的 `ChatMemoryRepository` 和本项目自定义的 `MyChatMemoryRepository`（仅一个 `optimization()`）。同一个对象：
- 通过 `ChatMemoryRepository` 类型被 `MessageWindowChatMemory` 当底层仓库用；
- 通过 `MyChatMemoryRepository` 类型被 `RecordOptimizationAdvisor` 注入，调用 `optimization()` 清掉多智能体转发残留的最后 2 条消息（路由/专项转发产生的中间一问一答）。

这正是"接口类型引用只暴露接口定义的那部分能力"的实际落地：Advisor 声明成 `MyChatMemoryRepository` 就只看得见 `optimization()`，够用且不绑实现。

**可能追问：**

- 窗口裁剪和落库分别在哪一层发生？（裁剪在 `MessageWindowChatMemory.add`，落库在 `RedisChatMemoryRepository.saveAll`，先截断再整段写回）
- `saveAll` 为什么先删后写？（仓库契约按"全量"语义传入，需先删保证幂等；代价是每次对话写放大）
- 同一会话并发写会怎样？（读-改-写三步非原子，会有覆盖/丢更新；单线程没问题，分布式需加锁或用追加式结构）
- 为什么要把仓库抽象成 `ChatMemoryRepository` 接口而不是让窗口直接用 Redis？（存储实现可替换、便于单测与隔离；本项目正因如此又加了一个 `MyChatMemoryRepository` 扩展清理能力）
